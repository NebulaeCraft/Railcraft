# 连续弯轨联挂车辆减速问题排查与修复记录

记录日期：2026-07-16

更新日期：2026-07-17

本文记录 Railcraft 1.12.2 项目中，联挂车辆经过连续转角轨道时速度显著下降的问题，以及本次对话中完成的原因分析、修复和验证。

## 对话目标

本次工作分为两个阶段：

1. 用户首先要求只分析原因，不修改项目。
2. 确认原因后，用户要求尝试修复，并将最终过程记录到 `docs`。

## 现象与范围

问题主要出现在组成列车的联挂矿车上。单辆未联挂矿车经过普通弯轨时，原版轨道移动逻辑会重新投影水平速度方向，但基本保留水平速度大小，因此并不是本次显著减速的主要来源。

联挂列车进入连续弯轨后，不同车辆会同时处于不同的轨道切线方向。旧联挂物理没有区分这种正常转向和真正的车辆间相对运动，从而持续施加错误的弹簧力和阻尼力。

## 原因分析

问题集中在：

```text
src/main/java/mods/railcraft/common/carts/LinkageHandler.java
```

### 1. 使用直线弦长判断车钩压缩

旧代码使用两个矿车中心之间的三维直线距离：

```java
double dist = cart1.getDistance(cart2);
double stretch = dist - optDist;
```

在直轨上，车辆中心直线距离可以近似表示沿轨距离。但在弯轨上，两辆车之间的直线是弦，必然短于沿轨道经过弯角的实际距离。

因此，即使车辆沿轨间距完全正常，`stretch` 仍会变成负数。联挂系统会把这种几何差异误判为车钩被压缩，并向车辆施加不必要的分离力。

### 2. 使用车钩弦方向计算相对速度

旧阻尼计算为：

```java
dot = (velocity2 - velocity1) · chordDirection
```

两辆车以相同速度通过弯道时，速度大小相同，但方向分别沿各自所在位置的轨道切线。世界坐标中的速度向量因此不同。

旧算法将这个正常的方向差投影到车钩弦方向后，会得到非零的“相对速度”，进而施加阻尼。该阻尼会不断消耗列车动能，所以连续弯角越多，速度下降越明显。

### 3. 同一个双向链接每 tick 被处理两次

链接由两端双向保存，而旧入口是每辆矿车触发一次的 `MinecartUpdateEvent`。因此一个 A-B 车钩通常会发生：

```text
A 更新时：调整 A-B
B 更新时：再次调整 B-A
```

这会在同一个 tick 内重复应用弹簧和阻尼，并可能混用一辆车的本 tick 位置与另一辆车的上一时刻位置，进一步放大弯道上的错误减速。

### 4. 其他相关因素

每辆联挂矿车仍会应用 `LINK_DRAG = 0.95`。这是既有的列车基础阻力，会造成稳定阻力，但它在直轨和弯轨上都会发生，不能单独解释连续弯轨中特别明显的额外减速，因此本次没有修改该参数。

机车使用上一时刻朝向施加牵引力也可能在转角处形成轻微放大效应，但不是主要根因，本次同样没有调整。

## 修复方案

### 1. 每个车钩每 tick 只计算一次

`MinecartUpdateEvent` 现在只记录本 tick 更新过的矿车及其是否位于弯轨。

实际联挂计算延迟到 `WorldTickEvent` 的 `END` 阶段执行。此时本世界中的矿车均已完成位置更新，并使用无序车辆 ID 对生成车钩键，确保同一个链接只处理一次。

这样同时消除了重复施力和新旧位置混用。

### 2. 识别弯道链接

两辆正在运动的车辆速度切线不平行时，才将链接视为弯道状态。这样既能覆盖一辆车刚离开弯轨、另一辆车尚未进入弯轨的过渡阶段，也不会把由连续转角方块组成的对角直线误判成持续转弯。

Minecraft 1.12.2 的单个转角轨道内部使用一段对角线作为矿车路径。连续交替摆放的转角轨道可以组成一条长对角直线；此时相邻车辆的速度切线保持平行，应继续使用完整的直线弹簧和阻尼。仅根据车辆是否位于转角方块判定弯道，会错误禁用车钩的压缩推力，使机车无法充分向后方矿车传递牵引力，并在基础联挂阻力下逐渐降到较低的平衡速度。

### 3. 消除弦长造成的伪压缩

弯道状态下，负的弹簧伸长量被限制为零：

```java
stretch = Math.max(0.0, distance - optimalDistance);
```

这意味着弯道上仍然保留车钩拉伸力，但不会因为弦长短于沿轨距离而产生错误的压缩力。直轨仍保留原来的双向弹簧行为。

### 4. 弯道阻尼改为沿各自切线计算

直轨继续使用原有的弦向相对速度阻尼。

弯道状态下改为：

1. 比较两辆车的水平速度大小，而不是直接相减世界坐标速度向量。
2. 将阻尼调整沿每辆车自己的运动切线施加。
3. 两辆车速度大小相等时，即使切线方向不同，也不会产生阻尼。

对于速度恰好为零的车辆，没有可用的速度切线。此时使用车钩方向和另一辆车的行进方向生成临时回退方向；下一次矿车轨道更新会把该速度重新投影到本车所在轨道的切线，因此静止车辆仍能在弯道上被牵引启动。

## 游戏内复测与二次修正

首次修复后，游戏内使用“机车 + 矿车”联挂组合复测时发现：列车经过由连续转角轨道组成的长斜线后，速度会逐渐下降到较低的固定值，回到普通直道后恢复正常。

原因是首次修复把“任一车辆位于转角轨道”也作为弯道链接的判定条件。长斜线上的每个轨道方块虽然都是转角形状，但 Minecraft 实际让矿车沿这些方块组成的同一条对角直线运动，相邻车辆的速度切线保持平行。错误的弯道判定持续截断了负弹簧伸长量，连带取消了车钩用于传递机车牵引力的有效压缩推力，最终使牵引力与基础联挂阻力在较低速度处达到平衡。

二次修正移除了轨道方块形状条件，只根据相邻车辆的实际速度切线是否不平行来判断链接是否跨越弯道。由连续转角组成的长斜线因切线平行而使用完整的直线联挂物理，真正跨越方向变化的车辆对仍使用弯道修正。

## 三次修正：斜线与直线交界处车辆位置互换

后续游戏内复测发现，机车与矿车在斜线和直线轨道交界处有概率穿过彼此，最终以相反顺序继续行驶。

问题由弯道压缩修正和既有碰撞规则共同造成：

1. 两车分别位于斜线和直线时，速度切线相差约 45 度，链接会被正确识别为弯道状态。
2. 旧弯道修正把所有负伸长量截断为零，因此从正常弦长缩短直到车辆中心重叠都没有压缩弹簧力。
3. `MinecartHooks` 为避免联挂物理与实体碰撞互相干扰，会忽略直接联挂车辆之间的碰撞响应。
4. 两车一旦在离散 tick 中穿过彼此，车钩弦方向会随新坐标反转；链接本身不记录前后顺序，之后的直轨弹簧会把车辆稳定在已经互换的位置。

这一现象不稳定复现，是因为是否在有限的弯道判定窗口内完成穿越，取决于进入交界时的精确间距、机车牵引力、速度修正和实体更新时序。

修复保留了弯道弦长补偿，但新增了 `1.28` 格的安全压缩区。该距离与普通矿车碰撞系统使用的静止距离一致：

```text
distance >= optimalDistance     使用正常拉伸弹簧
1.28 <= distance < optimalDistance
                                忽略弯道弦长造成的伪压缩
distance < 1.28                 恢复压缩弹簧，阻止车辆互相穿透
```

对于目标间距本身短于 `1.28` 格的特殊车辆，安全距离会限制为目标间距，避免安全区反过来把车辆推离其合法静止位置。

没有重新启用直接联挂车辆的常规碰撞；这样可以避免碰撞处理与车钩弹簧重复施力，同时仍由联挂物理提供维持最低中心距离所需的分离力。

## 建议的游戏内复测

自动测试验证了物理公式和项目构建，但不能完全替代 Minecraft 世界中的实体、区块和网络同步行为。建议使用修复前出现问题的同一条线路进行以下对比：

1. 相同机车、车辆数量、载荷和燃料条件下，记录直轨稳定速度。
2. 记录进入连续弯轨前、弯轨中部和离开弯轨后的速度。
3. 分别测试机车牵引和机车推行列车。
4. 测试列车从弯轨上完全静止后重新启动。
5. 测试一节、两节和较长列车，观察车钩是否出现异常拉长、重叠或振荡。

预期结果是：连续弯轨不再产生与弯角数量相关的显著额外减速，同时直轨牵引和车钩拉伸行为保持正常。
